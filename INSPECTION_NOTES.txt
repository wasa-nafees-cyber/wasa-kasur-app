Officer App - Patch Notes

Changes in this patch:
1. Consumer numbers entered through the officer recovery form must be exactly 5 ASCII digits (0-9). The field is limited to 5 characters and shows a numeric keyboard on mobile.
2. Recovery submission rejects malformed consumer numbers and blocks duplicate consumer numbers. If the duplicate lookup cannot be completed, submission fails closed instead of silently skipping the check.
3. Admin activity editor includes an Admin-only Recovery Officer reassignment selector. It updates the activity's officerName, officerPhone and officerRole so reporting attribution follows the selected officer.
4. Attribution changes are recorded in the existing editHistory, available in the admin panel. No notification is sent. Audit history is intentionally retained for accountability; it is not exposed as a separate notification to officers or management.
5. Admin activity editing also rejects malformed consumer numbers and blocks duplicate numbers instead of offering an override.

Validation performed:
- JavaScript syntax checks passed for officer-app.html and admin-panel.html.
- ZIP integrity test passed after packaging.

Important deployment/security note:
- This app uses client-side Firestore access. A query-then-write duplicate check can still race if two devices submit the same number simultaneously. To guarantee uniqueness, enforce it with trusted server-side logic / a Firestore transaction or security rules appropriate to the deployment.
- UI restrictions are not a substitute for Firebase Authentication and Firestore Security Rules. Review rules before production deployment. This patch does not claim a full production security audit.

SECURITY WARNINGS (existing design, NOT changed in this update)
---------------------------------------------------------------------
1. No Firebase Authentication. Passwords are stored as plain text in wasaUsers
   (field "passHash" is NOT a hash) and compared in the browser.
2. Super-admin phone/password, a default admin login (03001234567 / admin123)
   and the developer key are written inside admin-panel.html / officer-app.html.
   Anyone who opens the page source can read them.
3. Because of (1), Firestore rules must stay open for the app to work, so any
   person who has the Firebase project id can read or delete all data
   (including every password). firebaseConfig is public by design; only rules
   protect the data.
4. Officer "Search" downloads the WHOLE consumer collection (1 lakh docs) on each
   phone. 100 officers = millions of reads per day = real cost on Blaze.
5. Password-reset requests are saved in wasaPasswordResets but the admin panel
   has no screen to process them.
Recommended next step: move login to Firebase Authentication, then rewrite the
rules so officers can only create their own entries and only admins can read
users / delete data.
