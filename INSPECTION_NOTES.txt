Officer App - Patch Notes

Changes in this patch:
1. Consumer numbers entered through the officer recovery form must be exactly 5 ASCII digits (0-9). The field is limited to 5 characters and shows a numeric keyboard on mobile.
2. Recovery submission rejects malformed consumer numbers and blocks duplicate consumer numbers. If the duplicate lookup cannot be completed, submission fails closed instead of silently skipping the check.
3. Admin activity editor includes an Admin-only Recovery Officer reassignment selector. It updates the activity's officerName, officerPhone and officerRole so reporting attribution follows the selected officer.
4. Attribution changes are recorded in the existing editHistory, available in the admin panel. No notification is sent. Audit history is intentionally retained for accountability; it is not exposed as a separate notification to officers or management.
5. Admin activity editing also rejects malformed consumer numbers and blocks duplicate numbers instead of offering an override.

Validation performed:
- JavaScript syntax checks passed for officer-app.html and admin-panel.html.
- ZIP integrity test passed after packaging.

Important deployment/security note:
- This app uses client-side Firestore access. A query-then-write duplicate check can still race if two devices submit the same number simultaneously. To guarantee uniqueness, enforce it with trusted server-side logic / a Firestore transaction or security rules appropriate to the deployment.
- UI restrictions are not a substitute for Firebase Authentication and Firestore Security Rules. Review rules before production deployment. This patch does not claim a full production security audit.

UPDATE v3.3 - FREE-PLAN CONSUMER DATA, LOGIN, OFFLINE, CORRECTION LOG (Nov 2026)
=====================================================================
WHY THE OLD UPLOAD STOPPED AT 79,000 / 97,000
 Firebase FREE plan allows per day: 50,000 reads, 20,000 writes, 20,000 deletes.
 The old upload wrote 1 document per consumer (and first READ all existing ones),
 so it hit the daily limit half way. GitHub only holds the app code, the consumers
 live only in Firestore.

NEW CONSUMER STORAGE (fits the free plan)
 - Consumers are saved in a few big blocks (about 5,000 each): 1 lakh = ~35 documents.
   Upload / replace = ~35 writes. Loading = ~35 reads, and only CHANGED blocks are
   downloaded again. Collections: wasaConsumerMeta, wasaConsumerChunks.
 - Admin > Dashboard > "Consumer Data": Upload / Replace, Delete All Consumers
   (type DELETE), Delete old-format consumers (the 79,000 / 97,000 from earlier
   uploads: ~20,000 per day on the free plan, click again each day).
 - Admin > Bulk Upload > Consumers: "Replace everything with this file" (monthly
   refresh) or "Keep existing, add only new". Duplicate Consumer No inside the file
   are skipped and can be downloaded.
 - Edit / delete / add a single consumer and approving a correction change only one
   block. Officers get the changed block automatically.
 - Officer phone and admin browser keep a saved copy (IndexedDB): Search works
   offline and opens fast; when online it checks for changes (1 read) and refreshes.

STAY SIGNED IN
 - Admin panel and officer app stay signed in after refresh/reopen until Sign Out.

OFFLINE + LIVE
 - Officer: forms and Correction Requests are saved on the phone first and sent
   automatically when internet returns ("N Pending"). Settings and sections are
   cached, so the app opens quickly even with no internet.
 - Admin: new Correction Requests / Pending accounts appear immediately (badge in
   the sidebar + a message), no refresh needed.

ADMIN > CORRECTION LOG (new, admin only)
 - Every correction request: officer, consumer, old -> new values, reason, decision
   (approved / rejected), who decided and when, and what was finally applied.
 - Period: today, yesterday, last 7 days, last 30 days, custom dates, all time.
   Filter by status and officer. Download Excel.
 - Requests made before this update show consumer number only if it was part of the
   change.

DASHBOARD DATA WINDOW
 - The dashboard used to read ALL activities every time (burns the free 50,000 reads).
   It now reads the last 35 days by default (selector: 35 / 90 / 365 days / All).

FREE PLAN LIMITS TO REMEMBER (per day, all users together)
 - 20,000 writes  = about 20,000 bill-delivery entries a day in total.
   Entries that cannot be sent stay on the phones and go automatically next day.
 - 50,000 reads   = officer Home/Activity load all of that officer's own past
   entries; with many entries this will hit the limit. Needs a date-limited query.
 Blaze (pay-as-you-go with a budget alert) removes the limits; typical cost for this
 app would be very small.

---------------------------------------------------------------------
SECURITY / COST WARNINGS (existing design, NOT changed in this update)
---------------------------------------------------------------------
1. No Firebase Authentication. Passwords are stored as plain text in wasaUsers
   (field "passHash" is NOT a hash) and compared in the browser.
2. Super-admin phone/password, a default admin login (03001234567 / admin123)
   and the developer key are written inside admin-panel.html / officer-app.html.
   Anyone who opens the page source can read them.
3. Because of (1), Firestore rules must stay open for the app to work, so any
   person who has the Firebase project id can read or delete all data
   (including every password).
4. Officer "Search" downloads the WHOLE consumer collection (1 lakh docs) on each
   phone: 100 officers = millions of reads per day = real cost.
5. Officer Home / Activity / Reports load ALL of that officer's past entries.
   With 1000 deliveries a day this grows fast (reads and slowness). Fix later with
   a date-limited query + a Firestore index.
6. Password-reset requests are saved in wasaPasswordResets but the admin panel
   has no screen to process them.
Recommended next step: Firebase Authentication, then rewrite the rules so officers
can only create their own entries and only admins can read users / delete data.

=== v5 (duty-hours Live Map + bill-payment notification) ===
* "Hidden" tracking is not technically possible: Android always shows a location-permission prompt and an
  on-screen/notification indicator whenever an app reads location, including in background. This cannot be
  bypassed by a PWA, a PWABuilder APK, or any web app. So this feature is visible-to-the-officer by OS design,
  not a secret. Treat officers' awareness of tracking as a given, not optional.
* Officer app pings its own location every N minutes (Admin > Live Map > interval, default 5) while the app is
  open, to wasaLiveTrack/{phone} (one doc per officer, with today's trail capped at 120 points - cheap on the
  free quota: 1 write per ping per officer, 1 doc read for the map).
* If GPS/internet is off, no ping is sent - the admin Live Map shows "Offline since HH:MM", which is itself the
  signal requested (no silent fallback, no deception).
* Admin > Live Map: officer list with Online/Idle/Offline status, a Leaflet map with live markers, and today's
  path when an officer is clicked. Tracking can be switched off entirely from this screen.
* New collection wasaLiveTrack added to firestore.rules - republish the rules.
* New notification "payment_recorded": fires automatically when a field entry's Amount field is > 0; editable
  like all other notification templates in Admin > Notifications & OTP (includes {amount}).
* Suggestion: get written acknowledgment from officers (e.g. in their joining letter) that the work app tracks
  location during duty hours, for your own legal protection — covert, undisclosed employee surveillance carries
  real labor-law risk and is not something this app can (or should) hide.
